# Plan Representation Analysis: JSON vs. Executable JavaScript

## Overview

This document explores two approaches for representing form-filling plans generated by the LLM: declarative JSON plans vs. executable JavaScript code.

---

## Alternative A: JSON Plan Representation

### Example Execution Path

```javascript
// 1. LLM analyzes form, returns JSON plan
const plan = {
  "formId": "signup-form",
  "steps": [
    {
      "stepNumber": 1,
      "fields": [
        { "selector": "#firstName", "action": "fill", "profileKey": "firstName" },
        { "selector": "#email", "action": "fill", "profileKey": "email" },
        { "selector": "#terms", "action": "check" }
      ],
      "navigation": { "action": "click", "selector": "#next-btn", "waitFor": "#step2" }
    },
    {
      "stepNumber": 2,
      "fields": [
        { "selector": "#address", "action": "fill", "profileKey": "address" },
        { "selector": "#state", "action": "select", "profileKey": "state" }
      ],
      "navigation": { "action": "submit", "selector": "#submit-btn" }
    }
  ]
};

// 2. Local executor interprets JSON
for (const step of plan.steps) {
  for (const field of step.fields) {
    const element = document.querySelector(field.selector);
    if (field.action === "fill") {
      element.value = userProfile[field.profileKey];
    } else if (field.action === "check") {
      element.checked = true;
    } else if (field.action === "select") {
      element.value = userProfile[field.profileKey];
    }
  }
  // Execute navigation
  if (step.navigation) {
    document.querySelector(step.navigation.selector).click();
    await waitFor(step.navigation.waitFor);
  }
}
```

### Pros
- **Declarative** - easy to inspect/debug
- **Safe** - limited action vocabulary prevents arbitrary code execution
- **Portable** - JSON can be cached, versioned, shared across instances
- **Validatable** - can schema-check before execution
- **LLM-friendly** - generating structured data is natural fit for current models

### Cons
- **Fixed vocabulary** - can't handle novel interactions outside predefined actions
- **Complex logic awkward** - conditional fills, dynamic selectors, retry logic requires expanding JSON schema
- **Interpreter complexity** - must build execution engine for all edge cases
- **Verbose** - multi-step forms create large JSON structures

## Alternative B: Executable JavaScript Code

### Example Execution Path

```javascript
// 1. LLM generates executable JS code
const generatedCode = `
async function fillForm(userProfile) {
  // Step 1: Personal info
  document.querySelector('#firstName').value = userProfile.firstName;
  document.querySelector('#email').value = userProfile.email;
  document.querySelector('#terms').checked = true;

  document.querySelector('#next-btn').click();
  await waitForElement('#step2');

  // Step 2: Address
  document.querySelector('#address').value = userProfile.address;
  const stateSelect = document.querySelector('#state');
  stateSelect.value = userProfile.state;

  // Handle dynamic dropdown
  if (!stateSelect.value) {
    // Fallback: find option by text
    const options = Array.from(stateSelect.options);
    const match = options.find(opt => opt.text.includes(userProfile.state));
    if (match) match.selected = true;
  }

  document.querySelector('#submit-btn').click();
}
`;

// 2. Execute generated code in sandboxed context
const sandboxedFunction = new Function('userProfile', 'waitForElement', generatedCode + '\nreturn fillForm(userProfile);');
await sandboxedFunction(userProfile, waitForElement);
```

### Pros
- **Maximum flexibility** - full JavaScript capabilities for edge cases
- **Compact** - code is more concise than equivalent JSON
- **Native error handling** - try/catch, conditionals, loops built-in
- **LLM strength** - code generation is well-established capability (see PAL, Code as Policies papers)
- **Handles complexity naturally** - dynamic selectors, conditional logic, retries

### Cons
- **Security risk** - arbitrary code execution (must sandbox carefully)
- **Harder to inspect** - user can't easily understand what will happen
- **Debugging complexity** - runtime errors in generated code harder to trace
- **Validation difficulty** - can't schema-validate executable code before running

## Caching & Specialization Comparison

| Aspect | JSON Plans | Executable JS |
|--------|-----------|---------------|
| **Cache storage** | ✅ Plain text, small size | ✅ Plain text, smaller size |
| **Version control** | ✅ Easy diffs, merge-friendly | ⚠️ Code diffs harder to review |
| **Site-specific agents** | ✅ Store plan per domain in `chrome.storage` | ✅ Store code per domain |
| **Manual editing** | ✅ Easy for humans to tweak selectors | ⚠️ Requires JS knowledge |
| **Plan validation** | ✅ Schema check before cache | ❌ Must execute to validate |
| **Reusability** | ✅ Share plans across users | ⚠️ Code review needed before sharing |

### Specialization Strategy (Either Approach)

```javascript
// Cache structure
const siteSpecificPlans = {
  "citywater.com": {
    lastUpdated: "2025-01-15",
    plan: {/* JSON */} // or code: "function fillForm..."
  },
  "powercompany.com": { ... }
};

// Execution decision tree
async function fillForm(url, userProfile) {
  const domain = new URL(url).hostname;
  const cached = await chrome.storage.local.get(domain);

  if (cached && !isStale(cached.lastUpdated)) {
    // Use cached plan/code
    return executeCached(cached.plan, userProfile);
  } else {
    // Generate new plan/code via LLM
    const plan = await generatePlan(url, userProfile);
    await chrome.storage.local.set({ [domain]: { plan, lastUpdated: Date.now() }});
    return execute(plan, userProfile);
  }
}
```

## Alternative C: Hybrid Approach (JSON + Escape Hatch)

**Best of both worlds:**

```json
{
  "steps": [
    {
      "fields": [
        { "selector": "#firstName", "action": "fill", "profileKey": "firstName" }
      ],
      "customLogic": "if (document.querySelector('#promo-code')) { document.querySelector('#promo-code').value = 'SPECIAL'; }"
    }
  ]
}
```

**Strategy:**
- Default to safe JSON actions for standard form interactions
- Allow optional `customLogic` field for JavaScript snippets when needed
- Sandbox execution of custom logic only
- Most forms use pure JSON, complex edge cases get JS escape hatch

**Trade-offs:**
- Pro: Safety by default, flexibility when needed
- Pro: Easy to audit (scan for `customLogic` fields)
- Con: Two execution paths to maintain
- Con: Still need sandboxing infrastructure

## Research Alignment

### Relevant Papers from agentic_feature_exploration.md

**Supporting JSON approach:**
- **ReWOO** (2305.18323): Structured planning phase with declarative plan generation
- **LLM+P** (2304.11477): Natural language → PDDL (formal declarative spec) → execution

**Supporting executable code approach:**
- **WebAgent** (2307.12856): Python program synthesis for web interactions
- **PAL** (2211.10435): LLM generates Python programs as reasoning steps
- **Code as Policies** (2209.07753): Generates executable Python for robot control
- **ProgPrompt** (2209.11302): Program-like specifications with executable outputs
- **SmartFlow** (2405.12842): Generates PyAutoGUI code for GUI automation
- **Selenium Form Filling** (2511.15168): Fine-tuned LLM generates Selenium scripts

**Pattern:** Most recent research (2023-2024) favors executable code generation over declarative plans.
